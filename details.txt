1. WHAT IS THIS PROJECT?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CodeSage AI is a full-stack, AI-powered code review and project scaffolding
platform. It combines:

  • A rich Monaco-based IDE workspace in the browser
  • AI-driven code review with severity scores and fix suggestions
  • A 3-agent pipeline that generates entire project repositories from a prompt
  • A persistent AI chat assistant with semantic search over any GitHub repo
  • GitHub OAuth integration for browsing, committing, and managing repos
  • In-browser code execution via WebContainers, CheerpX, and v86

The UI was originally named "AgentForge AI" on the landing page (LandingPage.tsx)
while the backend/package still identifies the product as "CodeSage AI".

2. THE CORE PROBLEM IT SOLVES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem 1 — Code review is slow and inconsistent.
  Traditional code reviews depend on human bandwidth. CodeSage submits any
  code snippet or GitHub file to an AI provider and gets back structured
  feedback: a numeric score (0–10), tagged issues (bug / security /
  improvement), severity levels, and concrete suggested fixes — in seconds.

Problem 2 — Project bootstrapping is tedious and error-prone.
  Starting a new project requires wiring together package.json, configs,
  source files, and deployment scripts. CodeSage's 3-agent pipeline (see §6)
  does this autonomously and pushes the result directly to a new GitHub repo.

Problem 3 — Context switching between editor, terminal, and AI chat.
  Developers waste time copying code into ChatGPT, waiting for a response,
  then manually applying changes. CodeSage integrates a Monaco editor, an
  in-browser terminal, and a persistent AI chat that can read your repo,
  suggest fixes, and apply them to files in one click.

Problem 4 — Vendor lock-in to a single AI provider.
  Rate limits, outages, or cost overruns from one provider block work.
  CodeSage has a 7-provider fallback chain so that if one fails, the next
  automatically picks up without user intervention.

4. AUTHENTICATION FLOW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The entire auth system lives in server/routes/auth.js.
The raw GitHub access token NEVER leaves the server.

Step-by-step OAuth flow:

  1. User clicks "Login with GitHub" → frontend redirects to GET /auth/github
  2. Server generates a CSRF state token (signed JWT, 10min TTL), stores it as
     an httpOnly cookie "oauth_state", then redirects browser to:
       https://github.com/login/oauth/authorize
       ?client_id=GITHUB_CLIENT_ID
       &scope=repo+read:user+user:email
       &state=<random>
  3. GitHub redirects back to GET /auth/github/callback?code=...&state=...
  4. Server validates CSRF state cookie vs query param (prevents CSRF attacks)
  5. Server POSTs to https://github.com/login/oauth/access_token
     to exchange the one-time code for a GitHub access_token
  6. Server fetches /user and /user/emails from GitHub API using the token
  7. Server UPSERTs user row into Supabase git_profiles table
     (user_id, provider='github', login, name, avatar, email, token, scope)
  8. Server issues its own JWT (7d expiry), stores it as httpOnly cookie
     named "codesage_token", then redirects browser to /dashboard?auth_success=1
  9. All subsequent requests carry "codesage_token" cookie automatically.
     The Express JWT middleware decodes it and attaches req.userId.

Additional auth endpoints:
  • GET  /auth/me     — verify cookie, return safe profile (no raw token)
  • POST /auth/logout — clear codesage_token cookie
  • POST /auth/pat    — save a Personal Access Token for GitLab/Bitbucket/Codeberg

Security notes:
  • Cookies are httpOnly (JS cannot read them)
  • In production: Secure=true, SameSite=none (cross-origin safe on Render)
  • In development: SameSite=lax (http localhost)
  • JWT secret is a 64-char random hex string (JWT_SECRET env var)
  • GitHub token stored server-side only (never sent to frontend)

5. DATABASE SCHEMA (Supabase / PostgreSQL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

All schema lives in supabase-setup.sql (run once in Supabase SQL Editor).

TABLE: public.git_profiles
  ─────────────────────────────────────────────────────────────────────────
  user_id       TEXT NOT NULL          — Primary user ID (GitHub numeric ID as text)
  provider      TEXT NOT NULL          — 'github' | 'gitlab' | 'bitbucket' | 'codeberg'
  provider_id   TEXT                   — User ID on that specific platform
  login         TEXT                   — Username / login handle
  name          TEXT                   — Display name
  avatar        TEXT                   — Avatar URL
  email         TEXT                   — Email address
  token         TEXT NOT NULL          — OAuth access token or PAT (encrypted at rest by Supabase)
  token_scope   TEXT DEFAULT ''        — OAuth scope string
  created_at    TIMESTAMPTZ DEFAULT now()
  updated_at    TIMESTAMPTZ DEFAULT now()
  PRIMARY KEY   (user_id, provider)    — Composite key: one row per user per provider
  ─────────────────────────────────────────────────────────────────────────
  AUTO-TRIGGER: set_updated_at() fires BEFORE UPDATE to keep updated_at fresh.
  RLS: ENABLED (service role bypasses, anon/client cannot read raw tokens).

TABLE: public.chat_threads
  ─────────────────────────────────────────────────────────────────────────
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid()
  user_id       TEXT NOT NULL          — References git_profiles.user_id
  owner         TEXT NOT NULL          — GitHub org/user that owns the repo
  repo          TEXT NOT NULL          — Repository name
  title         TEXT NOT NULL DEFAULT 'New Chat'
  created_at    TIMESTAMPTZ DEFAULT now() NOT NULL
  updated_at    TIMESTAMPTZ DEFAULT now() NOT NULL
  INDEX: idx_chat_threads_user_repo ON (user_id, owner, repo)
  AUTO-TRIGGER: set_updated_at() on update.
  ─────────────────────────────────────────────────────────────────────────

TABLE: public.chat_history
  ─────────────────────────────────────────────────────────────────────────
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid()
  thread_id     UUID REFERENCES chat_threads(id) ON DELETE CASCADE
  user_id       TEXT NOT NULL
  owner         TEXT NOT NULL
  repo          TEXT NOT NULL
  role          TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'system'))
  content       TEXT NOT NULL          — Message body
  fixes         JSONB DEFAULT '[]'     — Array of {path, content} AI-suggested file changes
  attachments   JSONB DEFAULT '[]'     — Array of base64 image strings (vision inputs)
  created_at    TIMESTAMPTZ DEFAULT now() NOT NULL
  INDEX: idx_chat_history_thread ON (thread_id, created_at)
  ─────────────────────────────────────────────────────────────────────────

Row Level Security:
  All three tables have RLS ENABLED.
  The backend uses SUPABASE_SERVICE_ROLE_KEY which bypasses all RLS policies.
  No client-side policies defined — direct client access to raw tokens is blocked.

7. 3-AGENT PROJECT SCAFFOLDING PIPELINE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Defined in: server/services/aiService.js → generateProjectWorkspace()
Triggered via: BullMQ agent queue (server/services/agentQueue.js)

When a user submits a "Generate New Project" request, three sequential AI calls
are made:

  Agent 1 — Dependency & Configuration Manager
    Input : Project name, description, tech stack, user prompt
    Task  : Generate ALL configuration files ONLY — package.json, tsconfig.json,
            .env.example, vite.config, webpack.config, etc.
    Output: { "files": [{ "path": "package.json", "content": "..." }] }

  Agent 2 — Code Architect / Developer
    Input : User prompt + list of files Agent 1 already created
    Task  : Write ALL application source code — components, services, routes,
            controllers. NO configuration files.
    Output: { "files": [{ "path": "src/App.tsx", "content": "..." }] }

  Agent 3 — Verifier & Fixer
    Input : List of all files from Agent 1 + Agent 2 combined
    Task  : Review for correctness, missing imports, consistency. Return ONLY
            files that need to be fixed or are missing. Return { "files": [] }
            if everything is correct.
    Output: { "files": [...fixed or new files...] }

  Final Merge:
    Combined files → Agent 3 overrides → unique file map → final file set

  After generation:
    1. Create a new GitHub repo via GitHub API
    2. Push all generated files as an initial commit
    3. Return { owner, repo } to the user

  Progress updates: BullMQ job.updateProgress() streams status strings like
    "Agent 1: Managing dependencies...", "Agent 2: Writing source code...", etc.

8. 3-AGENT CHAT PIPELINE (In-Repo AI Chat)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Defined in: server/controllers/projectController.js → handleChatProject()

When a user chats about a repo, a 3-agent pipeline runs:

  Step 1 — Fetch codebase context
    • Fetch repo tree via GitHub API
    • Filter out binaries, node_modules, .git, dist, etc.
    • Fetch up to 30 files' content in parallel batches of 5
    • Run semantic search (Xenova all-MiniLM-L6-v2) to find the 5 most relevant
      files for the user's query using cosine similarity

  Step 2 — Planner Agent
    • Provider: configured in settings (default: NVIDIA)
    • Task: Analyze the request and produce a step-by-step plan. No code yet.

  Step 3 — Coder Agent
    • Provider: configured in settings (default: Groq)
    • Receives: planner output + codebase context + chat history
    • Produces JSON: { "message": "...", "command": "...", "fixes": [...] }
    • Fallback: if Coder fails → Fallback Agent (default: OpenRouter)

  Step 4 — Persist to database
    • Save user message to chat_history
    • Save assistant response to chat_history (with fixes + command)
    • Thread updated_at timestamp updated

  Fixes format: [{ "path": "src/App.tsx", "content": "<full file content>" }]
  Command field: a shell command to run in the in-browser terminal
  Attachments: base64 images for vision-capable providers (OpenAI, Anthropic, Gemini)

9. SEMANTIC SEARCH ENGINE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Defined in: server/services/semanticSearch.js

Uses @xenova/transformers running the all-MiniLM-L6-v2 model (~90MB) locally
on the Express server (no external embedding API needed).

  • Model cached in server/.cache/ directory
  • Generates 384-dimensional sentence embeddings
  • Query: user's chat message
  • Documents: file path + first 1500 chars of content per file
  • Ranking: cosine similarity, descending
  • Returns: top K (default 5) most relevant files

This is how the chat agent knows WHICH files to include in the AI context window
instead of blindly sending all repo files.

11. GITHUB INTEGRATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Defined in: server/services/githubService.js, server/controllers/githubController.js
Routes: server/routes/github.js → /api/git/*

Operations supported:
  • Browse repositories (list user repos, search)
  • Fetch repo file tree (recursive)
  • Fetch individual file content (base64 decoded)
  • Commit a single file to a branch
  • Commit multiple files atomically (Git Trees API — no force push)
  • Create a new repository
  • Fix GitHub Actions workflow permissions (auto-run on AI fix push)

Multi-provider support (server/services/gitProviderService.js):
  GitHub, GitLab, Bitbucket, Codeberg — same interface, different APIs.
  Users can add PATs for additional providers via POST /auth/pat.

GitHub OAuth scopes requested: repo, read:user, user:email

12. IN-BROWSER CODE EXECUTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Three runtimes are available (user selectable):

  WebContainers (@webcontainer/api)
    • Component: src/components/WebContainerTerminal.tsx
    • Full Node.js environment running natively in the browser
    • Requires COOP/COEP headers (Cross-Origin-Opener-Policy, etc.)
    • Best for JavaScript/TypeScript/Node projects

  CheerpX (@leaningtech/cheerpx)
    • Component: src/components/CheerpXTerminal.tsx
    • x86 Linux emulation via WebAssembly
    • Can run native Linux binaries, Python, etc.
    • Slower startup, broader language support

  v86 (x86 PC Emulator)
    • Component: src/components/V86Terminal.tsx
    • Boots a real Linux ISO image (linux3.iso) via CDN
    • VITE_V86_ASSET_BASE: CDN for BIOS/WASM/seabios files
    • VITE_V86_LINUX_IMAGE: URL for the Linux disk image
    • Timeout configurable via VITE_V86_EXEC_TIMEOUT (default 120000ms)

Server-side execution: server/utils/dockerSandbox.js
  • Runs code in an isolated Docker container on the server
  • Used for /api/project/:owner/:repo/:branch/run and exec endpoints
  • Generates Dockerfiles using AI (generateDockerfileForProject)

17. KEY DESIGN DECISIONS & NOTES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. MONOREPO-LITE STRUCTURE
   Frontend and backend in the same Git repo. Vite builds frontend into /dist
   which Express then serves as static files. In dev, Vite (port 5173) and
   Express (port 3001) run separately with CORS.

2. JWT OVER SUPABASE AUTH
   Instead of using Supabase's built-in Auth, the server issues its own JWT
   after GitHub OAuth. This gives full control over the session and allows
   the GitHub token to be stored only on the server side.

3. NO FORCED PROVIDER
   The platform works with just ONE AI API key (Groq has a free tier). All
   7 providers are optional. The fallback chain ensures at least one works.

4. AI KEYS NEVER STORED SERVER-SIDE PER USER
   User-provided API keys live only in localStorage and are passed in the
   request body. The server never writes them to the database.

5. SEMANTIC SEARCH RUNS ON-SERVER
   Using @xenova/transformers avoids any external embedding API cost or latency.
   The model downloads once and caches in server/.cache.

6. DOCKER SANDBOX FOR SERVER-SIDE EXECUTION
   When the AI suggests fixes and the user wants to run the project on the
   server, Docker isolates each execution. The browser-side WebContainers/v86
   handle client-side execution without any server resources.

7. CROSS-ORIGIN HEADERS HANDLED CAREFULLY
   CORP: cross-origin is set globally. COEP is NOT set globally (would block
   CDN resources). Only specific pages that need SharedArrayBuffer opt in
   via HTML meta tags.

8. BRANDING INCONSISTENCY
   LandingPage.tsx and footer use "AgentForge AI" while server logs, package.json,
   and supabase-setup.sql say "CodeSage AI". These appear to be two iterations
   of the same product — "AgentForge" is the newer brand name.
